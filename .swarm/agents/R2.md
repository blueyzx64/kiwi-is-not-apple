## Findings for orchestrator

### F1 S1: wallpaper tint decode freezes the whole Shell (main loop) for the full decode time
- lib/wallpaperTint.js:129-133 (`GdkPixbuf.Pixbuf.new_from_stream_at_scale_async`).
- Trigger: a big wallpaper (or first login / scheme switch to an uncached picture). Measured in real Shell 50.6 (gdk-pixbuf 2.44.4 + glycin 2.1.5): 14000x14000 PNG: decode 4989 ms, max main-loop gap 4985 ms (the Shell is frozen the whole time). 1280x800: 51 ms / 27 ms gap. Evidence: /tmp/r2/ev/e2/last-run.txt ("== E2 wallpaper decode"); 8K realistic numbers in E5.
- Why: on this gdk-pixbuf the stream "async" loader does its decode on the calling (main) thread; it is not a worker thread as the header comment claims.
- Confidence: high (isolated: only Kiwi's _decode ran, white wallpaper shown).
- Fix: decode out of the Shell process or off the main thread: e.g. `Gio.Subprocess` running `gdk-pixbuf-thumbnailer`/`gjs` helper that prints the 32x32 average, or use GNOME's own background thumbnail (GnomeDesktop/`~/.cache/thumbnails` via `thumbnail::path` from `query_info_async`, already tiny) and average that; also cap by `GdkPixbuf.Pixbuf.get_file_info_async` dimensions (skip > e.g. 16 MP or fall back to the thumbnail).

### F2 S2: re-enabling Dash to Dock in the Extensions app while Kiwi's dock runs leaves BOTH docks running
- features/dock/dashToDock.js:85-91 + core/originals.js:347,352-359 (ListMembersOwner strips the uuid synchronously inside the `changed::enabled-extensions` emission).
- Trigger: `Main.extensionManager.enableExtension('dash-to-dock@…')` (what the Extensions app / `gnome-extensions enable` D-Bus call does). Result: DtD state ACTIVE (1), enabled-extensions without DtD, Kiwi dock also active. Stays that way (checked 8 s). Evidence /tmp/r2/ev/e1-last-run.txt "-- user re-enables DtD by hand": `en:2, dtdState:1, list:kiwi@kemma,probe@x2`.
- Cause: the Shell's async `_onEnabledExtensionsChanged` (extensionSystem.js:562) is still awaiting DtD's enable when Kiwi rewrites the key; the second pass does not see DtD in `_extensionOrder` yet (pushed after the await), so it is never disabled, and `_enabledExtensions` is then set to the stripped list. (An external `gsettings set` write is handled fine: dis increments.)
- Also: Extensions app now shows DtD on, but it is off at next login (not in the list).
- Confidence: high. Fix: do the strip from an idle (after the Shell finished its pass), and/or watch `Main.extensionManager` 'extension-state-changed' for the held uuids reaching ACTIVE and strip again from an idle; better UX: treat an explicit user enable of DtD as "user wants DtD" and turn Kiwi's dock off (yield like Auto Light/Dark).

### F3 S2: dark hard-edged rectangle behind glass menus (the menu-bar agent's artefact): reproduced
- Seen on Kiwi dock app menus (and the same mechanism for every attachMenu surface). Evidence: /tmp/r2/ev/e2/crop-dockmenu-dw.png (rect visible over the light Text Editor window), pixel step 222->179 at x=400,y=548, 4 px outside the box, square corners while the box radius is 14 px.
- Not the shadow host: removing `.kiwi-glass-shadow` from the BoxPointer bin or `box-shadow:none` on it leaves the step (E4 variants b/c, /tmp/r2/ev/e4/). The glass box's theme node still reports the Shell theme's OUTER shadow `0 2px 4px rgba(0,0,0,.2)` (gnome-shell-dark.css:923-928 `.popup-menu-content`), not Kiwi's inset rim: `St_BoxLayout.popup-menu-content kiwi-glass … shadow=0,2 blur4 inset false`. St paints an outer shadow of a gradient background from the prerendered texture with hard rectangular edges (exactly what base.css:23-25 warns about) -> the rectangle. E5 pins it (box-shadow:none inline).
- Fix: in styles/base.css give glass surfaces an explicit outer `box-shadow: none` that wins over the theme (or put the rim on a pseudo/child), and verify with get_theme_node().get_box_shadow() == null/inset on menus, the QS menu and the calendar.
